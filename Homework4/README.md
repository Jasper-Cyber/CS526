## Problem 1: Tree traversals

### Problem 1.1

```
              A
          /   |   \
        B     C     D
      /   \         |
     E     F        G
     |     |
     H     I
```

| Traversal | Rule | Sequence |
|---|---|---|
| Preorder | node, then each subtree left to right | **A B E H F I C D G** |
| Breadth-first | level by level, left to right | **A B C D E F G H I** |
| Postorder | each subtree left to right, then node | **H E I F B C G D A** |

How each sequence is built:

- **Preorder.** Visit A. Go into B's subtree: B, then E's subtree (E, H), then F's subtree (F, I). Then C. Then D's subtree (D, G).
- **Breadth-first.** Level 0: A. Level 1: B C D. Level 2: E F G. Level 3: H I. A FIFO queue gives this order. Each node is dequeued and its children are added to the back.
- **Postorder.** A node is written only after all of its children. H before E, I before F, then B. C has no children. G before D. The root A comes last.

### Problem 1.2

```
              A
          /       \
        B           C
      /   \           \
     D     E           F
      \              /   \
       G            H     I
```

**In-order (left subtree, node, right subtree): D G B E A C H F I**

How the sequence is built:

- In-order of B's subtree: D has no left child, so write D, then its right child G. Then B, then E. This gives **D G B E**.
- Then the root **A**.
- In-order of C's subtree: C has no left child, so write C. Then F's subtree: H, F, I. This gives **C H F I**.

### Checking the answers

`tree_traversals.py` builds both trees with node classes and runs a recursive preorder, postorder and in-order, and a queue-based breadth-first traversal. Its output matches the answers above. See [How to run](#run-problem-1-tree-traversals) for the command and output.

## Problem 2: Smallest number of elements whose sum is greater than T

### Algorithm

Sort the array in descending order. Add the elements one at a time, largest first. The answer is the number of elements added at the moment the running sum first becomes **greater than** T.

For the assignment example `[8, 3, 9, 2, 7, 1, 5]` with T = 18:

```
sorted: 9, 8, 7, 5, 3, 2, 1
k = 1:  9            =  9   not > 18
k = 2:  9 + 8        = 17   not > 18
k = 3:  9 + 8 + 7    = 24   > 18   ->  answer 3
```

### Why taking the largest elements is optimal

For any count k, no k elements of the array can have a larger sum than the k largest elements. So if any set of k elements has a sum greater than T, the k largest do too. If the k largest do not pass T, no set of k elements does. The first k where the sum of the k largest passes T is therefore the smallest possible answer. This also holds when the array contains negative numbers.

### Details

- **Strictly greater.** The comparison is `total > target`, as the problem asks. In `fewest_1.txt` (T = 17) the two largest values give 9 + 8 = 17, which is not enough, so the answer is 3, not 2.
- **Complexity.** Sorting takes O(n log n) and the scan takes O(n). The 10,000-element test runs instantly.
- **No answer.** The problem guarantees that the total is greater than T. If an input breaks that guarantee, the function returns `-1` instead of a wrong count.
- **Output.** The program prints the array as read (not sorted), the target and the answer on one line, in the format from the assignment:

```
Input: 8,3,9,2,7,1,5 Target: 18 Answer: 3
```

## Problem 3: Number of right triangles

### Algorithm

Every right triangle has **exactly one** 90° corner, because the other two angles add up to 90°. So every triangle can be counted once, at its right-angle corner:

1. Pick each point P in turn as the possible right-angle corner.
2. For every other point Q, compute the vector `(dx, dy) = Q - P` and reduce it to its direction by dividing both parts by `gcd(dx, dy)`. The sign is kept, so this describes a **ray** from P. For example, `(2, 4)` and `(3, 6)` both become `(1, 2)`, and `(-2, -4)` becomes `(-1, -2)`, a different ray.
3. Count how many points lie on each ray from P, using a `Counter`.
4. Turning a ray `(x, y)` by +90° gives `(-y, x)`. For every ray `r`, add `count[r] * count[r turned +90°]`. Each product is the number of point pairs (A, B) with a right angle at P.
5. The sum over all corners P is the answer.

Only the +90° turn is counted. If B is A turned by +90°, then A is B turned by −90°, not +90°. So each pair {A, B} is counted exactly once.

### Worked example (`rightangles_1.txt`)

Points: (0,0), (0,4), (0,7), (3,0), (9,0).

At P = (0,0), the rays are `(0,1)` with 2 points (from (0,4) and (0,7)) and `(1,0)` with 2 points (from (3,0) and (9,0)). Turning `(1,0)` by +90° gives `(0,1)`, which adds 2 × 2 = 4. Turning `(0,1)` by +90° gives `(-1,0)`, which has no points. No other point is the corner of a right angle, so the answer is **4**.

### Details

- **Complexity.** O(n²) time and O(n) extra memory, compared with O(n³) for checking every set of three points. The 1,000-point test takes about 1.4 seconds. On random tests, 2,000 points took 5.3 s and 3,000 points took 13 s, so the program stays under the 30-second limit up to about 4,000 points.
- **Exact integer arithmetic.** Directions are integer pairs reduced by the gcd, so there are no slopes, no division by zero for vertical lines and no floating-point rounding. Equal directions always produce the same dictionary key.
- **Degenerate triangles are never counted.** Three collinear points cannot have a 90° corner, because two rays on the same line are never perpendicular.
- **Decimal coordinates.** The test files use integers. If a coordinate such as `1.5` appears, every coordinate is read exactly as a `Fraction` and all points are multiplied by the common denominator. Scaling does not change any angle, so the count stays the same.
- **Repeated points.** The problem says the points are different. If a point is repeated anyway, it is kept only once, so a zero-length side never occurs.

### Note on `rightangles_3.txt`: 5295 vs. 5294

`answers_angles.txt` gives **5294** for the 1,000-point test, but this program prints **5295**. I checked the count with two other exact methods that do not share code with this solution:

| Method | Result |
|---|---|
| This program (gcd-reduced rays, O(n²)) | 5295 |
| Integer dot product = 0, for every corner and every pair of other points | 5295 |
| Pythagoras on exact squared distances, a² + b² = c², for all ~166 million triples | 5295 |

The input has 1,000 distinct points and no repeats. Each of the 5295 triangles has a different set of corners, so none is counted twice.

Common mistakes do not explain 5294 either. Leaving out the first point gives 5284 and leaving out the last point gives 5286. Checks that use floating point, such as matching `atan2` angles or squaring `sqrt` side lengths, give 3403 and 2338. Because three exact methods agree, I believe 5295 is the correct count and the answer file is off by one. The program is not adjusted to match it.

## Interesting aspects

- **Counting at the right angle (Problem 3).** Checking every set of three points is O(n³), about 166 million triples for n = 1,000, which is too slow in Python. A triangle has only one right angle, so counting at that corner counts each triangle exactly once. The work then becomes a hash-table lookup for each pair, O(n²).
- **Rays instead of lines (Problem 3).** Keeping the sign of the direction (rays, not lines through P) makes perpendicular pairs easy to count: each pair matches with a +90° turn, so no division by 2 is needed. If directions were normalised to lines through P, each perpendicular pair of lines would be found twice and the total would have to be halved.
- **Floating point gives wrong answers here (Problem 3).** On `rightangles_3.txt`, computing side lengths with `sqrt` and then checking `a**2 + b**2 == c**2` finds only 2338 of the 5295 triangles, because squaring a rounded square root rarely gives back the exact integer. All arithmetic in the solution uses integers for this reason.
- **A greedy choice that is provably optimal (Problem 2).** Sorting and taking the largest values is the obvious idea. The exchange argument above shows it is also correct, including with negative values, so no search over subsets is needed.
- **Tested against brute force.** Both programs were compared with brute-force versions on 400 random inputs each. For Problem 3 the inputs included negative and decimal coordinates. For Problem 2 they included negative values and inputs with no answer. All results matched.
- **Robust input handling.** Blank lines and Windows `\r\n` line endings are ignored. Input is read as UTF-8 and a leading byte order mark is dropped, because piping a file in PowerShell (`Get-Content file | python ...`) can add one, and `int()` would otherwise fail on the first line. In Problem 2, array values may be spread across several lines, and only the first n values are used.
